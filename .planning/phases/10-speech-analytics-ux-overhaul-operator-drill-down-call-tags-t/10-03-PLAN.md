<objective>
Make a project's call-topic taxonomy a real, editable, validated, persisted thing end-to-end: a manager types a theme and its synonyms in project settings (D-17), it is validated and stored on the project as a controlled vocabulary (D-13), and the queryable per-call tag table that later plans write into exists with the right shape and the right uniqueness and source semantics (D-19, D-22).

Purpose: everything downstream in the phase — auto-tagging at analysis, the «Темы» section, tag chips, the tag column in export — is dead without a taxonomy to match against and a table that survives re-analysis. Getting the storage shape wrong here is the phase's most expensive mistake: reusing the existing metric-values table for tags would silently delete every manual correction on the next analysis.
Output: two dialect migrations, one new model, one JSON column with validated DTO, one editor form, and the type additions both repos need.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → API | Theme ids, names, synonyms, colours and descriptions are entirely caller-authored and arrive on the project update endpoint |
| API → database | Taxonomy is stored as a JSON document on a tenant-owned project row |
| stored taxonomy → matcher | Synonyms authored here are later compiled into a matching expression by 10-05 |
| stored taxonomy → DOM | Theme names are later rendered as chips and card titles |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-03-01 | Elevation of Privilege | taxonomy write on another tenant's project | high | mitigate | The write rides the existing `updateProject`, which already resolves the project by id **and** owning user; no new endpoint and therefore no new authorisation surface (D-22, no new roles). |
| T-10-03-02 | Denial of Service | caller-authored synonym compiled into a matching expression | high | mitigate | Validation caps the synonym count per theme and the length of each synonym here, at the write boundary, so 10-05's matcher can never be handed a pathological input; 10-05 additionally escapes metacharacters. |
| T-10-03-03 | Tampering | stored cross-site scripting via a theme name rendered as a chip | high | mitigate | Length caps and control-character rejection at validation; names render as React children only and `dangerouslySetInnerHTML` is not introduced. |
| T-10-03-04 | Denial of Service | unbounded taxonomy document size | medium | mitigate | Theme count cap on the array plus per-field length caps, mirroring the existing custom-metrics cap. |
| T-10-03-05 | Tampering | analyses mislabelled with a bumped schema version | medium | mitigate | The taxonomy branch deliberately omits the version increment; a spec pair asserts the two branches diverge. |
| T-10-03-06 | Denial of Service | analysis path fails on a server missing the new column | high | mitigate | Reads default to an empty list and writes are wrapped in the repo's warn-and-continue pattern quoting the migration file name; both dialect migrations ship together and are recorded in `user_setup`. |
| T-10-03-07 | Information Disclosure | tag rows leaking across tenants once written | medium | mitigate | The table carries the owning user and project columns from creation so 10-05 and 10-07 can scope every read; uniqueness is per channel-and-tag, never global per tag. |
| T-10-03-SC | Tampering | package-manager installs | low | accept | This plan installs nothing; 10-RESEARCH.md § Package Legitimacy Audit records zero new packages for the phase. |
</threat_model>
