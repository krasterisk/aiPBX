<objective>
Give the dashboard the per-theme numbers the «Темы» section renders (D-15) and the numbers its drill-down panel summarises (D-16) — computed inside the existing dashboard aggregation, gated on a selected project (D-29), and costing no extra database work.

Purpose: the «Темы» section must agree with the stats row above it. Any separate endpoint would have its own filters, its own cache entry and its own opportunity to disagree, which is exactly the class of bug the phase is meant to remove. Folding the aggregation into the response that already carries every other dashboard section is what guarantees consistency.
Output: one pure aggregation lib with tests, one response-interface addition, and the gated wiring.
</objective>

  <behavior>
    - Given records where two themes each appear on some calls, the aggregation returns one entry per theme with the right call counts.
    - Each entry's average score is the average total score of the calls carrying that theme.
    - Each entry's successRate is the percentage of tagged calls where analytics.metrics.success is true, using the same scored denominator and two-decimal rounding as buildAgentScorecards.
    - Each entry's sentiment object reports positive, neutral, and negative counts (or shares) derived from analytics.sentiment or metrics.customer_sentiment on the tagged calls.
    - A dashboard request for a selected project includes the theme section in its response.
    - A dashboard request with no project selected omits the theme section entirely.
    - A project whose taxonomy is empty produces no theme section; a project with a taxonomy and no matching calls produces an empty theme list.
    - A period with zero scored calls yields zero for every derived number rather than a non-numeric value.
  </behavior>
  <action>
    Create the aggregation as a pure module taking the already-loaded call records and the project taxonomy, and returning one entry per theme. Read each call's theme list from the analysis JSON the dashboard already has in memory — deliberately not from the tag table. The dashboard is the most expensive endpoint in the module and it already holds every record it needs; adding a query per dashboard load to re-derive information sitting in those records would be the single worst cost decision available here. Compute per D-16 and RESEARCH Pattern 6: callsCount, averageScore, successRate, and sentiment: { positive, neutral, negative } — mirror buildAgentScorecards for success and sentiment derivation (analytics.metrics.success, analytics.sentiment or metrics.customer_sentiment, denom = scored || 1, parseFloat(x.toFixed(2))). Share-of-period and delta-vs-period-average may be included as additive optional fields but must not replace or omit the locked D-16 fields.

    Add the theme section to the dashboard response interface using the field name the frontend type already expects, so no adapter layer is needed on either side. Wire the aggregation into the dashboard assembly behind the project gate: compute it only when a project is selected, because the taxonomy lives on the project and there is nothing to aggregate against otherwise. Read the taxonomy off the project record the method already fetched — do not add a second fetch, and if the taxonomy is needed earlier than the existing fetch, move that fetch rather than duplicating it. Distinguish the two negative cases deliberately: omit the section when there is no project or no taxonomy, and return an empty list when there is a taxonomy but nothing matched, because the UI shows different guidance for each.

    Write the lib spec for the aggregation behaviours and extend the service spec for the gating behaviours.
  </action>

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-07-01 | Information Disclosure | theme statistics for another tenant's project | critical | mitigate | The aggregation runs inside `getDashboard`, downstream of its existing tenant scoping and its project resolution; it introduces no new query and therefore no new scoping surface. It reads only records the caller was already entitled to. |
| T-10-07-02 | Tampering | theme names echoed into the payload and later rendered | medium | mitigate | Names originate from the length- and content-capped 10-03 write boundary or from snapshots of those same values; nothing new is accepted here, and every consumer renders them as React children. |
| T-10-07-03 | Denial of Service | payload growth from a large taxonomy on the heaviest endpoint | medium | mitigate | Entry cap plus deterministic ordering; the aggregation is in-memory over records already loaded and adds no query. A spec asserts the invocation count is unchanged. |
| T-10-07-04 | Denial of Service | duplicate project fetch per dashboard load | medium | mitigate | The existing project fetch is reused or moved, never duplicated; a spec assertion on repository invocation counts enforces it. |
| T-10-07-05 | Information Disclosure | inferring a tenant's taxonomy from response shape | low | accept | The section is only ever computed for a project the caller already owns; an unowned project id resolves to nothing upstream. |
