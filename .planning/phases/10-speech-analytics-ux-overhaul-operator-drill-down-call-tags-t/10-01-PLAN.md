<objective>
Ship the backend read surface behind the operator drill-down panel: a bounded, tenant-scoped `GET /operator-analytics/operator-evidence` that aggregates per-metric quotes and rationales out of the `aiAnalytics.metrics` JSON blob for a single operator over the dashboard's own period (D-05), omitting metrics that have no evidence (D-08) and identifying the operator by exact name (D-04).

This is the phase's riskiest architectural claim — that per-metric evidence can be aggregated server-side, cheaply, without shipping transcripts to the browser. It is proven end-to-end here, on the first commit, before any UI depends on it.

Purpose: without this endpoint the «почему такая оценка» chain (D-02) has nothing to show, and the only alternative — aggregating client-side from `getOperatorCdrs` — would multiply PII exposure and payload for no benefit.
Output: one new HTTP read route, one pure aggregation lib with unit coverage, one Swagger DTO, an exact-operator filter option shared with later plans, and a documented sample cap.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → API | `operatorName`, `startDate`, `endDate`, `projectId`, `userId`, `limit`, `order` all arrive untrusted on a JWT-authenticated route |
| API → database | Filter values reach Sequelize `where` objects and two raw-SQL dialect branches |
| API → client | The response body carries verbatim customer speech extracted from analysed calls |
| API → logs | Audit lines leave the process and may be shipped to a SIEM |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-10-01-05 | Repudiation | untracked access to customer speech | medium | mitigate | Structured `AUDIT` log line per read in the `logTranscriptAccess` shape, naming actor, operator and record count, wrapped so it cannot break the read. |
