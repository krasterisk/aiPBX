<objective>
Make tags real on the backend: match a project's taxonomy against each freshly analysed transcript and persist the result in both places it is needed (D-14, D-19), keep manual corrections safe across re-analysis (Pitfall 1), expose a validated manual-edit route with the existing permission model (D-14, D-22), and give the list endpoint the theme and exact-operator filters the drill-down and journal surfaces need.

Purpose: the taxonomy from 10-03 is inert until something matches it, and the «Темы» report in 10-07 and every tag chip in 10-08 and 10-09 read what this plan writes. This is also where the phase's two sharpest backend risks live: a caller-authored synonym compiled into a regular expression, and a re-analysis silently deleting a manager's manual correction.
Output: one matcher with tests, automatic tagging wired into the analysis path, a manual update route, and two new list filters.
</objective>

  <behavior>
    - A transcript containing a theme's synonym as a whole word returns that theme.
    - A transcript containing the synonym only as part of a longer word returns nothing.
    - Matching ignores letter case on both sides, for Cyrillic and Latin text alike.
    - A synonym containing regular-expression punctuation matches that punctuation literally.
    - An empty or whitespace-only synonym matches nothing.
    - A theme matched by two different synonyms is returned once, not twice.
    - A transcript matching more themes than the per-call cap returns the cap, deterministically ordered.
    - An empty taxonomy, an empty transcript, or a theme with no synonyms returns nothing and does not throw.
    - Analysing a call for a project with a taxonomy writes the matched theme ids and a snapshot of their display names into the analysis topics block.
    - Analysing that call also inserts one automatic tag row per matched theme, carrying the owning user and the project.
    - A failure inserting tag rows leaves the analysis result intact and logs a warning.
    - Analysing a call for a project with no taxonomy writes no tag list and no tag rows.
  </behavior>
  <action>
    Add the taxonomy matcher to the existing keyword-spotting module rather than a new file, so both spotters share one normalisation and one place to reason about Russian text. Take a transcript and a taxonomy and return the matched theme ids. Escape every synonym before it becomes part of a pattern — synonyms are caller-authored through the project settings form and a raw synonym is a direct path to both a pattern-behaviour change and a catastrophic-backtracking stall. Skip any synonym that normalises to empty, because an empty alternative in a pattern matches every call and would tag the whole tenant with one theme. Detect phrase boundaries with an explicit character class covering Cyrillic letters, Latin letters and digits rather than a Unicode property escape: the backend compiles to a target that does not support property escapes with the Unicode flag, and the pattern would fail to compile at runtime. Deduplicate the result and cap the number of themes per call so one pathological taxonomy cannot blow up the analysis payload. Do not touch the existing compliance spotter's behaviour or its result field — that field feeds an existing export column and an existing test assertion, and the two concepts are different.

    Wire the matcher into the analysis persistence path next to where metric values are dual-written. Load the project's taxonomy from the project record already being read there, run the matcher over the same transcript text the compliance spotter uses, and write two things into the topics block: the matched theme ids, and a snapshot map from theme id to display name. The snapshot exists so a theme renamed or deleted six months later still renders correctly on historical calls, which is what D-20 requires. Then insert one automatic tag row per matched theme with the owning user and the project, using the duplicate-tolerant bulk insert so the uniqueness constraint from the previous plan does the deduplication. Wrap the whole tag side-write in the repo's warn-and-continue wrapper: a lagging server or a database hiccup must degrade to an untagged call, never to a failed analysis. Do not add any backfill, migration-time recompute, or on-read retroactive matching — historical calls stay untagged by decision, and adding it would rewrite analyses managers have already reviewed.

    Extend the keyword-spotting spec with the matcher behaviours and the service spec with the persistence behaviours.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| stored taxonomy → matcher | Caller-authored synonyms become part of a matching pattern executed against every transcript |
| client → API (manual edit) | A call id and a theme id list arrive untrusted on a mutating per-call route |
| client → API (list filters) | A theme id and an operator name arrive untrusted and reach the query layer |
| API → database | Tag rows are written per call with tenant and project ownership |
| API → logs | Audit lines for manual tag changes leave the process |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
